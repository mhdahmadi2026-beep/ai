# Prompt caching (docs.avalai.ir/fa/guides/prompt-caching)

Reduce latency and cost by letting the upstream provider reuse a processed prompt prefix. OpenAI claims up to ~80% latency / ~90% input-token cost reduction on eligible traffic — on AvalAI treat numbers as provider/model dependent and check the real `usage` fields of that route.

## Structure prompts for caching
Hits need an **exact prefix match**: static content (instructions, examples, tool definitions, long policy, image order/bytes) first; variable content (user-specific facts, timestamps, retrieved snippets, request ids) last. Images and tools must be identical between requests.
Models where AvalAI can expose provider caching (non-exhaustive, provider/route dependent): `gpt-5.6-sol|terra|luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5.4-pro`, `gpt-5.2`, `gpt-5.1`, `gpt-5-mini`, `gpt-4.1`, `gpt-4o`, `o3`, `o4-mini` (+ Claude/DeepSeek/Gemini routes). Availability, request controls, retention and discount vary per provider/route.

## How it works
Automatic for prompts above a provider-specific token minimum (OpenAI ≥1,024): routing by prefix hash (OpenAI: usually first ~256 tokens; `prompt_cache_key` combined with the hash improves locality) → lookup → hit reuses the prefix (cheaper/faster) or miss processes everything and may cache the prefix. OpenAI in-memory cache expires after ~5–10 min idle (max ≈1 h); non-OpenAI routes may differ.

## GPT-5.6 cost model & controls
OpenAI: cache **writes** on GPT-5.6 cost **1.25× normal input**; reported as `cache_write_tokens`; reads as `cached_tokens`. Pre-5.6 OpenAI models: no separate write fee. Upstream GPT-5.6 controls `prompt_cache_options`, `prompt_cache_options.ttl`, `prompt_cache_breakpoint` exist, but **AvalAI does NOT support explicit caching or explicit breakpoints → don't send those fields or provider-specific markers like `cache_control`**. The AvalAI catalog confirms prompt caching + write pricing for GPT-5.6 routes but not explicit control → use automatic implicit caching and measure via `usage`.

## Routing & retention on AvalAI (aggregator)
- A public model id may be served by several providers/infra pools. The smart router now remembers the last successful healthy route **per user + model + infrastructure** and prefers it for **15 minutes after the last successful request**; each success re-extends the window. Best-effort, not guaranteed (health, capacity, failover, availability or provider routing can move requests); the sticky window is only a routing preference and does NOT extend/guarantee the provider's own cache lifetime. (The Gemini section's table says "rolling ten-minute" — inconsistent; the main text says 15 minutes.)
- Propagation takes time: for `deepseek-v4-flash` a paired benchmark (2026-08-13, 15 s wait after priming, 2,000-token prefix, 10 rounds) reached the same warm cache-hit ratio as DeepSeek official (98.6% vs 98.6%; round 1: AvalAI 0% vs DeepSeek 98.6% — the official first response isn't a clean cold miss); `deepseek-v4-pro` first run stayed 0.0%, a later run 99.9% vs 98.6%. 15 s is an observation, not a deadline. App must work on cache misses; don't use cache affinity as conversation state. Details: performance page.
- `prompt_cache_key`: keep stable per workload/tenant/assistant config; avoid keys that funnel too much traffic (OpenAI: >~15 req/min per prefix+key may overflow to other machines → lower hit rate). Treat it as an opaque routing label, not user data: `support-policy-v3`, `tenant-acme-chat-v2`, `invoice-extractor-schema-v1`; never emails/phones/user ids/ticket ids/API keys/secrets; per-request ids go near the prompt end; rotate the key when policy/tool schema/prefix changes.
- Retention controls by generation: GPT-5.6+ → `prompt_cache_options.ttl` (not supported on AvalAI) and `prompt_cache_retention` is deprecated for them; pre-5.6 → `prompt_cache_retention` (`in_memory` | `24h`) where supported. Doc contradiction: the page's Python/Responses and Chat samples pass `prompt_cache_retention="24h"` with `gpt-5.6-luna` right after saying it's deprecated/unsupported for GPT-5.6 → **don't copy those samples**; the legacy retention example is meant for `gpt-5.5`-class models and only where AvalAI passes the param through. Omit it when unsure (rely on automatic in-memory caching).
- Extended retention (OpenAI): up to 24 h (usually expires after 1–2 h of use); may keep key/value tensors in GPU-local storage (not final responses). OpenAI lists extended-cache models: `gpt-5.5`, `gpt-5.5-pro`, `gpt-5.4`, `gpt-5.2`, `gpt-5.1-codex-max`, `gpt-5.1`, `gpt-5.1-codex`, `gpt-5.1-codex-mini`, `gpt-5.1-chat-latest`, `gpt-5`, `gpt-5-codex`, `gpt-4.1` — an upstream list, not an AvalAI guarantee. OpenAI prices in-memory and extended identically (verify usage/pricing of your route). Checklist: use `24h` only if AvalAI passes it; with models supporting both `in_memory` and `24h` choose deliberately (defaults differ under ZDR); ZDR/residency/regulated workloads → omit retention params until the route policy is confirmed; never use caching instead of storing conversation state/business records.

## Responses vs Chat patterns
Prefer Responses for new work; keep Chat when migration is risky (same caching principles: stable long system/developer prefix, tool schemas, image order, structured-output schema). Migrating: long shared instructions → `instructions` (or first stable input item); dynamic user text, retrieval snippets, timestamps, request ids near the end; same `prompt_cache_key` per assistant/tenant/policy/schema; read `usage.input_tokens_details.cached_tokens` (Responses) / `usage.prompt_tokens_details.cached_tokens` (Chat). Cache hit = optimization signal, not correctness.

## Requirements
Min tokens (below it requests still work, no cache read): OpenAI 1,024 · Anthropic Claude 3.x 1,024 · Claude Sonnet/Opus 4.x 2,048 · Claude Haiku 4.5+ & Opus 4.5+ 4,096 · Bedrock Claude 3.5/3.7 1,024 · Bedrock Claude Sonnet 4.x 2,048 · Gemini implicit 1,024. Anthropic thresholds vary by exact model: 512 (Opus 5, Fable 5, Mythos 5); 1,024 (Opus 4.8, Sonnet 5, Sonnet 4.6/4.5/4, Opus 4.1/4); 2,048 (Mythos Preview, Opus 4.7, Haiku 3.5); 4,096 (Opus 4.6/4.5, Haiku 4.5) → check the chosen route's model doc.
Usage example: `"usage":{"prompt_tokens":2006,"completion_tokens":300,"total_tokens":2306,"prompt_tokens_details":{"cached_tokens":1920,"cache_write_tokens":0},"completion_tokens_details":{"reasoning_tokens":0}}` (1,920 read from cache, none written). Responses: `usage.input_tokens_details.cached_tokens`; Anthropic-style: `cache_creation_input_tokens` / `cache_read_input_tokens` (both 0 → no caching on that request); native Gemini names differ.

## Measure
```text
cache_hit_ratio = cached_tokens / input_or_prompt_tokens
uncached_tokens = input_or_prompt_tokens - cached_tokens
```
Log by route, model, `prompt_cache_key`, stable prompt version: input/prompt tokens, `cached_tokens`, `cache_write_tokens` (if returned), output tokens, total, p50/p95 latency, request count; hit ratio of 2nd+ requests (1st = warm-up miss); error/fallback rate if a route rejects `prompt_cache_retention`. GPT-5.6: compute read and write cost separately — a write pays off only if later discounted reads cover the extra write cost; compare warm-up `cache_write_tokens` against later `cached_tokens`. Use metrics to split/rotate key buckets (a mixed high-traffic key causes overflow). Cached prompt tokens still count toward rate limits (TPM) and the response is regenerated every time.

## What can be cached (provider permitting) / invalidation
Tool definitions + order; system messages/long policy; message text blocks; user images/documents with identical bytes/order/settings; prior tool-use/tool-result blocks; prior assistant thinking blocks only when replayed with cacheable prior-turn content (can't be marked with `cache_control` directly). Citation sub-blocks can't be cached directly (cache the top-level document block); empty text blocks aren't cacheable; **explicit `cache_control` unsupported on AvalAI**.
Invalidation hierarchy `tools → system → messages`: changing tools invalidates tools+system+messages; web search/citations/speed-mode changes can invalidate system+messages; `tool_choice`, images and many thinking/effort controls invalidate messages; thinking-related invalidation of tools/system can be model-specific.

## Best practices
Static first / dynamic last; monitor `cached_tokens`, latency, hit rate; stable `prompt_cache_key` per prefix at a granularity under provider routing limits; keep tool defs, image order, structured-output schema, long policy text unchanged; per-request facts near the end; caching = optimization, not correctness.

## Troubleshooting cache misses
| symptom | likely cause | fix |
|---|---|---|
| short prompts never cache | below minimum cacheable length | combine fixed instruction/schema/reference context until prefix is long enough |
| long prompts miss every time | dynamic values too early | move user text/timestamps/retrieval/request ids after the fixed prefix |
| tool-heavy requests miss | tool schema/order changed | keep tool names/descriptions/schemas/order identical |
| image requests miss | image order, URL/base64 bytes or `detail` changed | same representation + same `detail` for the shared prefix |
| hit rate drops under load | one `prompt_cache_key` has too much traffic | split keys by assistant/tenant/workload |
| only one provider misses | route doesn't expose caching details via AvalAI | check provider page, drop unsupported retention params |
| hit rate much lower than direct provider | affinity still propagating, failover moved the request, or provider cache differs | retest after propagation window, log model/timing/`usage`, then open a support ticket |

## Gemini context caching
Implicit vs explicit: **implicit** — automatic, savings not guaranteed, no setup, no TTL control, AvalAI ⚠️ best-effort (same router affinity); **explicit** (`/cachedContents`, `cachedContent` reference, guaranteed savings, TTL) — **NOT supported on AvalAI** (aggregator distributes across infra; explicit caching needs persistent storage tied to specific infra, consistent routing and lifecycle management). Implicit caching is on by default for Gemini; Google applies savings automatically on a hit. Min tokens: Gemini 3 Flash Preview 1,024 · Gemini 3 Pro Preview 4,096 · Gemini 2.5 Flash 1,024 · Gemini 2.5 Pro 4,096 (model ids partly stale — verify). Tips: big static content first (system instructions, reference docs, few-shot examples); send similar requests close in time; dynamic content (user info, variable queries, timestamps, unique ids) last.
Check hits (native API, base `https://api.avalai.ir`): Python `response.usage_metadata.prompt_token_count / cached_content_token_count / candidates_token_count`; JS `usageMetadata.promptTokenCount / cachedContentTokenCount / candidatesTokenCount`; cURL `POST /v1beta/models/gemini-2.5-flash:generateContent` (page sample uses `Authorization: Bearer`; other v1beta pages use `x-goog-api-key` — both worked per earlier pages; prefer the SDK). Good use cases: chatbots with big system persona/KB, repeated questions over the same documents, code/repo analysis, many questions on the same media file.

## FAQ (OpenAI-based)
1) Privacy: caches generally aren't shared across organizations; benefits depend on how the upstream provider handles requests from AvalAI infra. 2) Doesn't change output — only prompt processing is optimized; response regenerated each time. 3) No manual cache clear; caches expire after idle. 4) Cost: no write fee before GPT-5.6; GPT-5.6 writes 1.25× + discounted reads — check both `cache_write_tokens` and `cached_tokens`. 5) Cached tokens still count toward TPM rate limits. 6) Discounts depend on provider/tier (OpenAI: standard + Scale Tier, not Batch API). 7) ZDR: provider/model/retention-mode dependent — confirm route before promising. 8) Residency: OpenAI in-memory caching doesn't store prompt data on disk; extended caching under regional inference must stay in region; AvalAI → verify route/region/retention before committing. 9) `prompt_cache_key` shouldn't identify individual users; opaque workload/tenant/assistant/policy/schema buckets; rotate on policy/tool/prefix change. 10) Don't rely on cache for correctness or continuity.
